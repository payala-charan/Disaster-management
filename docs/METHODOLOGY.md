# Methodology (generated)

Generated by `python -m app.tools.gen_docs` from the module docstrings: the code and this document describe the same rules. Do not edit by hand.

## Deterministic engines (no LLM)

### Priority score

Source: [`backend/app/engines/priority.py`](../backend/app/engines/priority.py)

Transparent priority score (0-100). Deterministic: the LLM never sets or changes a score.

| Factor                | Max | Rule (highest matching tier wins) |
|-----------------------|-----|-----------------------------------|
| Threat to life        | 25  | trapped / stranded / injured / water_rescue -> 22; isolated / cut_off -> 18; evacuation_needed -> 12; property_damage_only -> 5; none -> 0 + "Confirm threat to life" |
| People affected       | 20  | unknown -> 0 + "Confirm number of people affected"; 0 -> 0; 1-9 -> 5; 10-24 -> 8; 25-49 -> 14; >=50 -> 20 |
| Access route          | 15  | best KNOWN route status for the zone (engines/access.py): open 0; partially_blocked 8; closed 15; unknown / only inferred 10 + "Route verification required" |
| Weather / escalation  | 15  | severe warning AND heavy rain forecast (>=10 mm/h within 6 h) -> 13; heavy rain now or forecast -> 10; moderate rain (>=2.5 mm/h) now or forecast -> 5; none -> 0; +2 if wind >= 50 km/h (cap 15); no weather data -> 0 + verification |
| Infrastructure impact | 10  | main road closed 8; road partially flooded 6; power/utility loss 6; any other reported issue 4; none 0 |
| Response gap          | 15  | nothing assigned 15; assigned units below the estimated requirement (engines/resources.py) for any type, or an unmet external need -> 8; adequately covered 0 |

Levels: Critical >= 75, High 55-74, Moderate 35-54, Low < 35.
The level is overridden to `verification_required` (the score is still shown) when the location is
unknown, OR confidence is low AND the report is unverified AND it is not linked to a verified incident.

Each factor records the text value and the provenance of its input. `reasons` are templated
sentences built from the highest-scoring factors; the LLM may rephrase them but may not add facts.

Seed scenario results (asserted in tests/engines/test_priority.py):
- INC-003: 18 + 20 + 15 + 13 + 8 + 15 = 89, Critical.
- INC-002: 22 + 8 + 0 + 13 + 0 + 15 = 58, High.
- INC-001: 12 + 14 + 8 + 13 + 6 + 8 = 61, High. The original UI mock showed 53 (Moderate) because it
  treated BOAT-001 + TEAM-001 as full coverage. By the documented rule, 40 people need 5 boats and
  2 teams while 1 of each is assigned, so the response gap is 8.

### Zone accessibility

Source: [`backend/app/engines/access.py`](../backend/app/engines/access.py)

Zone accessibility from the road registry.

Rules:
1. Only roads with provenance `known` determine a zone's access status. The BEST known status wins
   (open > partially_blocked > closed): one open known road means the zone is reachable.
2. If no known road has a definite status, `reported` roads (e.g. a field-team observation) are used,
   but the result keeps provenance `reported` and asks for verification.
3. If neither exists, status is `unknown` -> "Route verification required".
4. `inferred` roads (AI-derived potential problems) NEVER set the status. They are listed separately
   as `inferred_issues`, and an inferred alternative to a blocked zone produces a verification item.
   This keeps a known closure and an AI guess from ever looking equivalent.

OSRM travel times are a separate concern (integrations/routing.py). OSRM does not know about flood
closures, so this registry result always overrides it.

### Duplicate detection

Source: [`backend/app/engines/duplicates.py`](../backend/app/engines/duplicates.py)

Duplicate detection between incident reports.

score = 0.35 x distance_score + 0.25 x time_score + 0.15 x type_match + 0.25 x text_similarity
- distance_score  = max(0, 1 - d / DUPLICATE_DISTANCE_M), d = haversine metres (0 if a location is unknown)
- time_score      = max(0, 1 - |dt| / DUPLICATE_TIME_WINDOW_MIN)
- type_match      = 1 if the incident types are equal, else 0
- text_similarity = rapidfuzz token_set_ratio(title + description, lowercased, punctuation stripped) / 100

Classification: score >= 0.70 -> potential_duplicate; 0.50-0.70 -> related; below 0.50 -> not linked.
The result only proposes a link for HUMAN review. Nothing is ever merged or deleted automatically.

### Resource state machine and requirement estimation

Source: [`backend/app/engines/resources.py`](../backend/app/engines/resources.py)

Resource lifecycle (state machine) and resource-requirement estimation.

## State machine
    available -> reserved      (coordinator approves an action)
    reserved  -> deployed      (action started)
    reserved  -> available     (approval cancelled)
    deployed  -> returning     (task finished, heading back)
    returning -> available     (back at base)
    any       -> unavailable   (breakdown, crew off duty, ...)
    unavailable -> available   (back in service)
Anything else (including X -> X) raises InvalidTransition. The API turns that into HTTP 409.

## Requirement estimation (every number carries its formula)
Let n = people_affected.
- Water rescue is needed when assistance includes water_rescue or evacuation AND
  (the incident is a flood whose known access is closed/partially blocked, OR people are stranded).
    rescue_boat = ceil(n / 8)           (nominal boat capacity 8)
    rescue_team = 1 + floor(n / 30)
- Otherwise, if evacuation is requested, it is by road:
    emergency_vehicle = ceil(n / 10)    (nominal vehicle capacity 10)
    rescue_team       = 1 + floor(n / 30)
- People trapped (landslide, collapse, fire) need search and rescue:
    rescue_team = 1 + floor(n / 30)     (the larger of this and any value above)
- Medical help requested (medical_check / medical / first_aid / medical_transport) or people injured:
    ambulance = max(1, ceil(n x 0.05))
- Fire needs fire-fighting units. The registry has none, so this is reported as an EXTERNAL need
  ("request fire services") and is never turned into an invented resource.
- n unknown: each needed type gets the minimum of 1 unit, marked verification_required, and
  "Confirm number of people affected" is added. The count is never guessed.

### Shelter calculations

Source: [`backend/app/engines/shelters.py`](../backend/app/engines/shelters.py)

Shelter capacity calculations. Available capacity is always derived and never stored.

- available    = max(0, capacity - current_occupancy)
- utilization  = current_occupancy / capacity (0 when capacity is 0)
- approaching_threshold = utilization >= SHELTER_ALERT_THRESHOLD (default 0.85)
- accepting    = status 'open' and available > 0
- can_accommodate(n) = accepting and available >= n
- crossed_threshold: true only on the update that moves utilization from below the threshold to
  at/above it, so the capacity alert fires once rather than on every later update.
- nearest_with_capacity: nearest accepting shelter (haversine) able to take n people.

### Allocation and alternative plans

Source: [`backend/app/engines/allocation.py`](../backend/app/engines/allocation.py)

Resource allocation: three alternative plans built only from resources that actually exist.

## Inputs
Prioritised incidents (priority + requirement estimate + zone access + already-assigned resources),
the resource registry, and optional travel estimates per (resource, incident), e.g. from OSRM.
Only resources with status `available` are considered.

## Need per incident
remaining(type) = required units (engines/resources.py) - units of that type already assigned.

## Feasibility
- Known closure of every known route (`ZoneAccess.ground_access_possible` is False): resources without
  the `water_rescue` capability (ambulances, vehicles, ...) cannot be sent by road. The need stays
  unmet with an explicit reason; no alternative route is invented.
- Boats are allowed but ALWAYS carry the assumption BOAT_ASSUMPTION: nominal capacity alone never
  establishes that water conditions are safe.
- Partially blocked access: allowed, with an assumption that travel may take longer.
- Unknown/unconfirmed access, unknown people count or a verification_required level: the allocation is
  flagged `verification_required`.
- Unknown location: nothing is allocated; it becomes a verification task.
- Pending potential duplicates (`duplicate_of` set) get no separate allocation, so the same people
  are not counted twice. The plan states this as an assumption.

## Candidate ranking (per needed type)
1. capability match (water_rescue preferred when boats are needed), 2. travel time (provided estimate,
or haversine x 1.3 at 30 km/h labelled "estimated"), 3. larger capacity, 4. resource ID (determinism).
A `used` set guarantees no resource appears twice within a plan.

## Variants
- A Priority-first: incidents by score (desc); each gets its full remaining need before the next.
- B Coverage: first one unit of each needed type to every critical/high incident (score order),
  then top up all incidents in score order.
- C Verified-access only: allocate (priority-first) only where access is decided by KNOWN road data
  and the level is not verification_required. Other incidents become verification tasks.

## Shortages (identical in every plan: they describe the situation, not the plan)
For each resource type: required = sum of remaining need over allocatable incidents,
available = count of `available` resources of that type, deficit = required - available (listed if > 0).
The note recommends escalation and never names an invented resource.

## Plan score (used only to pick the recommended plan)
plan_score = 100 x sum(priority_score_i x coverage_i) / sum(priority_score_i), where
coverage_i = allocated units / remaining required units (incidents with no remaining need are skipped).
Highest score is recommended; ties go to the earlier variant (A, then B, then C).

### Replanning impact analysis

Source: [`backend/app/engines/replanning.py`](../backend/app/engines/replanning.py)

Impact analysis for a changed condition. Pure: it only reports what is affected; the replanning
service (Phase 5) records the change, supersedes actions, raises alerts and starts a new run.

Rules:
- Road change -> incidents in the road's zone are reassessed (the access factor depends on it).
- Weather change -> incidents in that zone are reassessed. The caller sets `worsened` using
  weather_worsened(old, new): a severe warning appears, current or forecast peak rain rises by
  >= 5 mm/h, or wind crosses 50 km/h.
- Resource becomes unavailable -> actions that include it are affected; their incidents are reassessed.
  Resource becomes available -> every active incident with a pending action is reassessed (new capacity).
- Shelter change -> only when a shelter stops accepting people (full/closed) are incidents that
  requested evacuation reassessed.
- Incident update -> that incident is reassessed.

Action handling (human-in-the-loop is preserved):
- `pending` actions of affected incidents are SUPERSEDED: a fresh recommendation replaces them.
- `approved` / `in_progress` actions are never changed automatically. When the change worsens their
  conditions they are listed for coordinator REVIEW.

### Distance and travel estimates

Source: [`backend/app/engines/geo.py`](../backend/app/engines/geo.py)

Distance and travel-time estimates (pure math, no network).

- Haversine great-circle distance on a sphere of radius 6,371,008.8 m (mean Earth radius).
- Fallback travel estimate when OSRM is unavailable: road distance ~= straight line x 1.3
  (a common detour factor), driven at 30 km/h (cautious speed in flood conditions).
  The result is always labelled source="estimated" so it is never mistaken for routed data.

## Integrations

### LLM (OpenAI) usage and fallback

Source: [`backend/app/integrations/llm.py`](../backend/app/integrations/llm.py)

LLM integration (Gemini or OpenAI): the ONLY place the LLM is called.

Providers (LLM_PROVIDER):
- gemini: Google Gemini through its OpenAI-compatible endpoint, using the Chat Completions API
  (`chat.completions.parse` with a Pydantic response_format for structured output). Key: GEMINI_API_KEY.
- openai: OpenAI Responses API (`responses.parse`). Key: LLM_API_KEY.
- none:   deterministic fallback only.
Both providers go through the same `openai` SDK, so no extra dependency is needed.

The LLM is used for exactly four things (design rule 1):
  extract_incident  - structured fields from free text      (structured output -> ExtractedIncident)
  classify_threat   - threat-to-life labels                 (structured output -> ThreatClassification)
  explain           - human-readable rewording of a recommendation
  sitrep_narrative  - situation-report narrative

Graceful degradation (design rule 8): if LLM_PROVIDER is "none", the key is missing, or a call
fails or times out (LLM_TIMEOUT_S, default 10 s), every method returns the deterministic fallback
(regex extractor / template text) with llm_used=False and confidence "low". Nothing here raises to callers.

Free text is grounding-checked: any ID or number not present in the input context -> discarded,
template used instead (grounded=False is recorded for the agent trace).

The API key is read from Settings only. It is never logged, printed or included in error messages.

### Grounding check

Source: [`backend/app/integrations/grounding.py`](../backend/app/integrations/grounding.py)

Grounding check for LLM free text: every ID and number it mentions must exist in its input.

If the model mentions BOAT-009 or "120 people" and neither appears in the context it was given,
the text is discarded and the deterministic template is used instead.

Number matching:
- IDs are removed before numbers are extracted, so "INC-003" does not contribute "003".
- A percentage n% is accepted if n or n/100 appears in the context (0.85 <-> 85%).
Known limitation (documented): spelled-out numbers ("twelve") are not checked.

### Fallback extractor

Source: [`backend/app/integrations/fallback_extract.py`](../backend/app/integrations/fallback_extract.py)

Deterministic regex/keyword extractor: the fallback used when the LLM is unavailable.

Deliberately conservative: it only fills a field when a clear pattern matches. Results are always
marked confidence "low" by the caller.

People count: only an explicit number followed by a people word (people, persons, residents,
individuals, villagers, children, adults) counts. "About 25 people" -> 25 (as reported).
When several counts are stated ("2 people trapped ... 15 residents need relocation") the largest is
used, since people_affected means everyone affected and smaller groups are usually part of it.
Ranges ("10-15 people"), families and houses are NOT converted into a count: the value stays null.

### Weather (Open-Meteo)

Source: [`backend/app/integrations/weather.py`](../backend/app/integrations/weather.py)

Weather per zone: Open-Meteo (live, no API key) or simulation data.

Live request:
  GET https://api.open-meteo.com/v1/forecast?latitude=..&longitude=..
      &current=temperature_2m,precipitation,rain,wind_speed_10m,weather_code
      &hourly=precipitation,wind_speed_10m&forecast_hours=6
  (wind in km/h and precipitation in mm are Open-Meteo's defaults)

Derived values (documented thresholds, not an official warning service):
- rainfall_mm_per_hr = current precipitation (mm over the last hour)
- condition: >= 10 mm/h "Heavy rain", >= 2.5 "Moderate rain", > 0 "Light rain", otherwise from weather_code
- severe_warning = 6-h peak rain >= 20 mm/h OR wind (now or forecast) >= 60 km/h OR thunderstorm code (95/96/99).
  Open-Meteo has no official warnings, so this is a derived flag and the summary says so.

Modes and degradation:
- WEATHER_MODE=simulation: readings come from the simulation source (scenario data plus injected changes).
- live: results are cached for WEATHER_CACHE_MIN minutes per zone. On any failure the last good reading
  is returned (stale=True, keeping its original source and fetched_at); if there is none, the simulation
  reading is used. `fallback_reason` always says why, so the UI and trace can label it.

### Routing (OSRM)

Source: [`backend/app/integrations/routing.py`](../backend/app/integrations/routing.py)

Travel distance/time between points: OSRM public server, with a labelled estimate as fallback.

Live:  GET {OSRM_URL}/table/v1/driving/{lng,lat;...}?sources=..&destinations=..&annotations=duration,distance
       one request for a whole resources x incidents matrix (the public demo server allows ~100 coordinates).
       A single pair uses /route/v1/driving/{lng},{lat};{lng},{lat}?overview=false.
Fallback (ROUTING_MODE=simulation, timeout, error, or a null cell): haversine distance x 1.3 at 30 km/h,
       labelled source="estimated" (engines/geo.py).

IMPORTANT: OSRM knows nothing about flood closures. Travel times say how far a place is, never
whether it is reachable. Reachability comes only from our road registry (engines/access.py), which
always overrides OSRM. This module never constructs alternative routes.

### Geocoding

Source: [`backend/app/integrations/geocoding.py`](../backend/app/integrations/geocoding.py)

Resolve where an incident is. Order of preference:

1. Explicit coordinates in the report (e.g. an IoT sensor or field-team payload) -> provenance "reported".
2. Zone gazetteer (data/seed/zones.json): an explicit zone name, or a gazetteer alias found in the text
   ("river street" -> Zone D). The zone centre is an approximation -> provenance "inferred".
3. Optional Nominatim lookup (GEOCODING_NOMINATIM=true): at most 1 request/second, identifying
   User-Agent, provenance "inferred". Off by default because the demo district is fictional.
4. Otherwise the location stays unknown (None) with "Location unknown: confirm incident location".
   Never a guessed point.

## Agents and orchestration

### Workflow graph

Source: [`backend/app/graph/workflow.py`](../backend/app/graph/workflow.py)

LangGraph orchestration of the eight agents.

    START -> incident_intake
          -> [weather_intelligence | geospatial_accessibility | resource_management]   (parallel fan-out)
          -> situation_assessment                                                      (join)
          -> resource_allocation -> reviewer_critic
          -> (blocking findings and attempts left ? resource_allocation : emergency_coordination)
          -> END  (pending actions now wait for a coordinator)

Why severity runs after the fan-out: the priority score uses weather (escalation factor), road access
(access factor) and current assignments (response gap). Running it after all three have finished is
the simplest ordering where every score uses this run's data, with no second severity pass.

Human approval is NOT a graph node: the run ends with `pending` actions in the database, and the
coordinator approves them later through the API (Phase 5). That approval can happen hours later, from
another process, so persisted actions are the hand-off point rather than a paused graph.

Checkpointing: an in-memory checkpointer keeps every step's state for inspection during the process
lifetime. Each invocation gets a UNIQUE thread_id ("RUN-001:<uuid>"): run IDs restart after a database
reset, and reusing a thread would resume the old checkpoint and merge stale state into the new run. In production, use `langgraph-checkpoint-postgres` so that
state survives restarts.

CLI: python -m app.graph.workflow --mermaid docs/agent_graph.md

### Shared workflow state

Source: [`backend/app/graph/state.py`](../backend/app/graph/state.py)

Shared workflow state: the 'blackboard' agents communicate through.

Agents never call each other. Each node reads the keys it needs and returns only the keys it changed;
LangGraph merges them. Values are plain JSON (model_dump(mode="json")) so checkpoints are portable
and readable; agents rebuild Pydantic models when they need them.

Keys written by parallel nodes (trace, alerts_to_emit, changes, errors) use `operator.add` as a reducer
so concurrent updates are appended instead of overwriting each other.

| key | written by | content |
|---|---|---|
| run_id, trigger, new_report_ids | runner | run identity and what started it |
| new_incident_ids, incidents, duplicate_candidates | intake | normalized incidents (IncidentFacts), proposed duplicate links |
| weather | weather | zone -> WeatherFacts |
| zone_access, access_analysis, travel, shelter_options, isolated_zones | geospatial | access per zone/incident, travel matrix, nearest shelters |
| resources, resource_summary, shelter_status | resource_mgmt | registry state with assignments |
| requirements, assessments | severity | RequirementEstimate and PriorityAssessment per incident |
| plans, excluded_resource_ids | allocation | three PlanDrafts (+ explanation) |
| critic_findings, critic_iterations, blocking | critic | findings per plan variant |
| plan_ids, recommended_plan_id, pending_actions, summary, unresolved | coordination | persisted results |
| alerts_to_emit, changes, errors, trace | any (appended) | persisted by coordination / runner |

### Agent machinery and trace

Source: [`backend/app/agents/base.py`](../backend/app/agents/base.py)

Shared machinery for the eight agents.

- `Deps`: everything an agent may use (DB session factory, LLM, weather, routing, geocoder, settings, clock).
  It is passed to the graph as LangGraph *context*: it is available to every node but never stored in
  checkpoints, so the API key and DB connections never end up in workflow state.
- `StepRecorder`: records each tool call (name, args, result summary, ok) and whether the LLM was used.
- `@agent(name)`: wraps an agent function. It opens its own DB session (parallel nodes run in threads
  and SQLAlchemy sessions are not thread-safe), times the work, commits, and writes one `agent_steps`
  row. If the agent raises, its DB work is rolled back, the error is recorded, and the workflow
  continues with what it has (graceful degradation).

### 1. Incident Intake

Source: [`backend/app/agents/intake.py`](../backend/app/agents/intake.py)

Agent 1: Incident Intake. Normalizes raw reports from five source types into incidents.

Per raw report (status 'received'):
1. Build the text to read: free text plus any descriptive payload fields (observation, message, ...).
2. Area-wide government advisories (payload with `areas` and no specific location) do not become rescue
   incidents: they become a warning alert, because inventing an incident or a people count is not allowed.
3. Extract fields: structured payload fields are used as given (an explicit `people_count: null` stays
   null); free text goes through the LLM (with regex fallback). IoT sensor events are mapped
   deterministically (water_level -> flood).
4. Geocode (coordinates -> zone gazetteer -> unknown). Unknown location stays None.
5. Confidence and verification are set by documented source rules:
     field_team / government_alert: confidence high if type and zone are known, verification 'verified'
       for field teams, otherwise 'pending'
     emergency_call: extractor confidence (max medium), 'pending'
     citizen_report and iot_sensor: confidence low, 'unverified'
6. Provenance: counts and places stated in the report are 'reported'; labels derived from free text
   (threat, assistance, infrastructure) and approximated locations are 'inferred'.
7. Duplicate detection against all active incidents; links are created for HUMAN review only.
8. Field-team road observations are logged as 'reported' condition changes. They never overwrite the
   road registry, which only holds known facts.
A report whose incident type cannot be determined is marked 'failed' and listed for manual review.

### 2. Situation Assessment & Severity

Source: [`backend/app/agents/severity.py`](../backend/app/agents/severity.py)

Agent 2: Situation Assessment & Severity.

Runs AFTER the weather, geospatial and resource agents (the graph joins them first), so every score
uses this run's weather, access and assignment data. It only calls deterministic engines:
estimate_requirements -> assess_priority. The LLM never sets a score.

History: a new priority_assessments row is stored only when score, level or verification items changed,
so the history shows real changes. Alerts:
- critical_incident when an incident becomes critical,
- severity_increase when its level rises (low < moderate < high < critical).

### 3. Weather & Environmental Intelligence

Source: [`backend/app/agents/weather_intel.py`](../backend/app/agents/weather_intel.py)

Agent 3: Weather & Environmental Intelligence.

For every zone with an active incident: get the current reading (Open-Meteo or simulation, via the
weather tool), store new live readings, and compare the newest snapshot with the previous one.
If the newest snapshot arrived since the last completed run and is worse (engines/replanning.py:
weather_worsened), a weather_worsening alert and a condition change are emitted. That is what makes
the Severity agent reassess with the new data.

### 4. Geospatial & Accessibility

Source: [`backend/app/agents/geospatial.py`](../backend/app/agents/geospatial.py)

Agent 4: Geospatial & Accessibility.

- Zone access from the road registry (engines/access.py). Known closures and AI-inferred issues are
  reported in separate lists and never treated as equivalent.
- Travel matrix from available resources to incidents (OSRM table, or labelled estimates). OSRM says
  how far, never whether a closed zone is reachable.
- Nearest shelters per incident with PostGIS ST_DistanceSphere.
- Isolated zones: zones whose known routes are all closed.

### 5. Emergency Resource Management

Source: [`backend/app/agents/resource_mgmt.py`](../backend/app/agents/resource_mgmt.py)

Agent 5: Emergency Resource Management.

Reports the registry as it is now: every resource with its status and current assignment (from active
reserved/deployed assignments), counts by type and status, expected availability of returning or
unavailable units, and shelter capacity state (engines/shelters.py).

### 6. Resource Allocation & Response Planning

Source: [`backend/app/agents/planning.py`](../backend/app/agents/planning.py)

Agent 6: Resource Allocation & Response Planning.

Builds the allocation inputs from the other agents' outputs and calls the deterministic allocation
engine, which returns plans A/B/C with shortages and a recommended plan. The LLM then writes the
recommended plan's explanation FROM THE PLAN JSON ONLY (grounding-checked). The other two plans get the
template text, which saves cost and latency.

On a critic loop-back, resources the critic found invalid (e.g. no longer available in the database)
are excluded before re-planning.

### 7. Emergency Coordination & Action

Source: [`backend/app/agents/coordination.py`](../backend/app/agents/coordination.py)

Agent 7: Emergency Coordination & Action.

Consolidates the run into persisted results. NOTHING is dispatched and no resource is reserved here.

1. Choose the recommended plan: the highest plan_score among plans WITHOUT blocking critic findings
   (ties: A, then B, then C). If every plan has blocking findings, no actions are created.
2. Supersede the previous recommendation: earlier 'proposed' plans become 'superseded', and earlier
   'pending' actions become 'superseded' (with an audit event). Approved / in-progress actions are never
   touched: they are human decisions.
3. Persist plans A/B/C (with critic findings) and create one PENDING action per incident that the
   recommended plan allocates resources to. Each action carries rationale, assumptions, inputs used
   (with provenance) and a review deadline: critical 30 min, high / verification required 60, moderate 120, low 240.
4. Persist the alerts and condition changes collected by all agents.
5. Produce a situation summary and the list of unresolved issues (unallocated needs, verification items).

### 8. Reviewer / Critic

Source: [`backend/app/agents/critic.py`](../backend/app/agents/critic.py)

Agent 8: Reviewer / Critic. Deterministic checks on every plan before anything reaches a human.

| check | severity | rule |
|---|---|---|
| double_allocation | blocking | a resource appears more than once in a plan |
| resource_validity | blocking | resource unknown, not 'available' in the DATABASE NOW, or already actively assigned |
| capability | blocking | allocated type is not one the incident requires |
| route_claim | blocking | a resource without water capability sent to a zone whose known routes are all closed |
| boat_assumption | blocking | boats allocated without the boat-verification assumption |
| shortage_math | blocking | deficit != required - available, or a shortage with no deficit |
| priority_consistency | blocking | recomputing the priority from the run's inputs gives a different score/level |
| unsupported_claim | blocking | an explanation names an ID or number not present in the plan (grounding check) |
| stale_access | warning | the road registry changed during the run (a new run will follow) |
| agent_contradiction | warning | an incident has no weather or access result from the other agents |
| shelter_capacity | warning/info | people needing evacuation exceed free shelter space / shelters at threshold |
| verification | info | allocations flagged verification_required |

Blocking findings on resources (validity) feed `excluded_resource_ids`, and the graph routes back to
allocation (at most MAX_ITERATIONS times). Coordination never turns a plan with blocking findings
into actions.

## Services (API side)

### Human approval workflow

Source: [`backend/app/services/actions.py`](../backend/app/services/actions.py)

Human-in-the-loop action workflow. Only these coordinator calls change an action's state:

    pending --approve--> approved --start--> in_progress --complete--> completed
    pending --reject--> rejected          pending --modify--> pending (different resources)
    any open --reassess--> (new agent run; pending actions get superseded by it)
    any --comment--> (audit note only)

Approve is where resources are actually reserved, and it is protected twice against double allocation:
1. Row locks: `SELECT ... FROM resources WHERE id IN (...) ORDER BY id FOR UPDATE`. Two concurrent
   approvals touching the same resource are serialised, and the second one sees the first's result.
   (Locking in ID order means two approvals can never wait on each other in a deadlock.)
2. Database constraint: the partial unique index on active assignments rejects a second
   reserved/deployed assignment even if application code had a bug.
Either way the coordinator gets HTTP 409, the stale action is superseded, and a new run re-plans.
Every step writes an action_events row (who, what, when, comment).

### Dynamic replanning

Source: [`backend/app/services/replanning.py`](../backend/app/services/replanning.py)

Dynamic replanning: the one path every changed condition goes through.

handle_change():
1. records a condition_changes row (what, old -> new, provenance),
2. asks the pure impact engine (engines/replanning.py) what is affected,
3. marks affected PENDING actions 'superseded' (audit event explains why),
4. adds a review note to affected APPROVED / IN-PROGRESS actions. They are never changed
   automatically, because they are human decisions, so the coordinator decides,
5. returns the impact. The caller commits and, if impact.trigger_run, starts a new agent run, which
   reassesses priorities and publishes an updated recommendation.

### Operational changes and alert rules

Source: [`backend/app/services/operations.py`](../backend/app/services/operations.py)

Changes to the operational picture: roads, resources, shelters, weather, incidents, duplicates, intake.

Each function validates, applies the change in ONE transaction, raises the documented alerts, goes
through replanning.handle_change for anything that can affect a plan, commits, then broadcasts.
It returns the impact so the API can start a new agent run when needed.

Alert rules:
- route_blocked: a road becomes closed (critical) or partially blocked (warning) and that is a worsening
- resource_unavailable: a resource becomes unavailable (critical if it was assigned, else warning)
- shelter_capacity: utilization crosses SHELTER_ALERT_THRESHOLD (warning); shelter becomes full or closed (critical)
- weather_worsening / critical_incident / severity_increase: raised by the agents during the run
Manual resource changes may only set 'available' or 'unavailable'. Reserving, deploying and returning
happen through the action workflow, so the audit trail stays complete.
